committed that runs from a clean checkout. Status markers are updated as work lands.

## Why these choices

- **Quantizable torchvision models.** `torchvision.models.quantization` ships
  ResNet-18, MobileNetV2 and GoogLeNet variants that already contain the hooks
  real INT8 conversion needs (quant/dequant stubs, fusable blocks, quantization-safe
  residual adds). In FP32 they compute exactly what the standard models compute, so
  the baselines are fine-tuned on these variants and the same weights are quantized later.
- **224 px.** Grad-CAM's resolution is the last conv layer's grid, which is the
  input size divided by 32: 2x2 at 64 px, 4x4 at 128 px, 7x7 at 224 px. A 4x4 map
  makes top-k% IoU and SSIM very coarse, so 224 px (MedMNIST+ native size, also the
  ImageNet pretraining size) is the default. `data.size` in the config can switch it.
- **Three seeds and a noise floor (M0, M4).** A similarity of, say, 0.8 between
  FP32 and INT8 heatmaps only means something next to how much heatmaps differ
  between two FP32 models trained with different seeds. That comparison turns
  "heatmaps changed" into "heatmaps changed more (or less) than retraining would
  change them".

All choices, with alternatives, are logged in [DECISIONS.md](DECISIONS.md).

## Known risks

- PyTorch is moving quantization from `torch.ao.quantization` to `torchao` (PT2E).
  Real INT8 CPU kernels through PT2E need `torch.compile`, which on Windows needs a
  C++ toolchain. M1 uses eager-mode quantization, which runs without a compiler.
  The pinned Windows build (2.14.1+cu130) offers only the `onednn` quantized
  engine (no `fbgemm`/`x86`). A quick check during M0 confirmed that eager-mode
  prepare, calibrate and convert run under `onednn` for all three quantizable
  models (random weights; the check is not a result).
- 2-bit post-training quantization will likely destroy accuracy. That is a result,
  not a bug, but heatmap comparisons on a model at chance level need care (M4).
